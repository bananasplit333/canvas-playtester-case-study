Canvas Playtester
Claude Code case study

Teaching Claude to play-test a canvas game

At my studio, Claude Code could write game code but couldn't check its own work. I built a command-line tool, a Claude Code skill and a set of working rules so it can launch a game, play it the way a person does, measure what's on screen and show proof.

Role sole author Stack Node, Chrome DevTools Protocol, PIXI.js Scope ~2,200 lines, ~35 commands
The problem

The agent was working blind

Our slot games draw everything into a single WebGL canvas. There are no buttons in the DOM, so a browser agent has nothing to select. In practice Claude would:

  • click at pixel coordinates read off a screenshot. Slow, and it broke whenever the layout moved.
  • guess at art offsets. On one feature it rewrote the same offsets four times and missed every time, and I put my original numbers back.
  • hand the checking back to me: "can you send a screenshot?", "should this be bigger or smaller?"

So I was still doing all the QA. The goal was to let the agent verify its own changes and give me evidence instead of questions.

What I built

Three layers, each with one job

tool

A game-driving CLI

Controls Chrome over the DevTools Protocol and reads the game's PIXI scene graph directly. It finds things by visible text or component type, clicks with real mouse events, waits on real game state and records audio and console errors.

skill

A verify skill

Tells Claude when to verify (after any view, asset, animation or audio change) and how: build, launch, drive, assert, report. It also has a troubleshooting section that maps each known failure to its cause.

memory

Rules from corrections

Every time I corrected the agent, the correction became a written rule, and often a new command. That way the same mistake can't come back in the next session.

The loop

What Claude does after every change

static checksassets, strings, audio wiring
→
build + launchreal dev harness
→
playclick, spin, wait for state
→
measurelayout, audio order, errors
→
evidencescreenshot per finding

Every check exits non-zero when something is wrong, so a failure stops the run and gets reported. It can't slip by unnoticed.

Corrections that became rules

The skill grew from real mistakes

What went wrongWhat changed
Clicking at screenshot coordinates was slow and flaky.Rule: always drive games through the CLI. Clicks target scene nodes by text or type, never by pixel.
The agent asked me how big new art should be.New measuring commands read each panel's real border from the art's transparency, then scale and center the element with even padding, and can write the result to config. Sizing stopped being a judgment call.
Long translated strings clipped in dialogs.A language flag on launch, plus a saved test run that screenshots every dialog in the longest-text language, in both orientations.
Four guessed offset rewrites all missed.Rule: read the real layout data first, make one informed change, then measure. No guessing again.
A background browser was left running after a quiet shutdown.Rule: never silence the quit command, and confirm the debug port is actually closed.
Findings came back as a table I couldn't judge.Rule: every visual failure comes with its own screenshot and a caption, because some flags are intended art and I make that call.
A real run · 16 Nov 2026

From a mockup to a placed splash screen

The setup: a new splash screen has its frames and header in place and a design mockup to match. The panel content (two titles, the coin art, a description and the wild art) has been added to the config with no placement at all. Everything sits at native scale, piled on the center of its panel. Claude's job was to get from there to the mockup without anyone placing anything by hand.

Claude found that the existing fit command couldn't do this. It sizes one element against neighbors that are already placed, and here nothing was. So Claude added a stack command (about 40 lines) that lays out a whole panel from scratch, rather than placing the assets by hand.

The stack command orders elements by config order, gives them one shared scale (capped by panel width) and spaces them evenly. It is not pixel-identical to the mockup: the even-gap rule made the coins about 9% larger than the hand-tuned version. This was a landscape-only demo. Afterwards the original configs were restored and checked against their original hashes. The log is trimmed for width, with long names shortened and some columns dropped.

A feature test · 16 Nov 2026

Buying the bonus and entering Hold & Win

Claude played into a feature the same way a player would. It clicked the bonus buy button, confirmed the purchase, dismissed the feature intro and let the first Hold & Win respins play out. Each step waits for the real on-screen state before moving on. The video below is a recording of that run, captured by the tool itself, with no edits.

The CLI had no way to record video, so Claude added a record command. It captures the page's own frames over the DevTools Protocol while another command runs, and encodes them to MP4.

The clicks target the bonus buy button by its component type and the dialog buttons by their text, then fire real mouse events at those points. None of the coordinates were written by hand. The recording stops during the respins to keep it short. After recording, Claude played the rest of the feature through to the win screen off camera and checked again for console errors, so the next session doesn't resume halfway through the feature. The sleep steps exist only to make the video easy to follow.

In use

Three example runs

Swapping splash-screen art

New art was a different size from the old. Before, this meant several rounds of me eyeballing it. Now Claude measures the panel, fits the art and writes the numbers for landscape and portrait, then re-measures until nothing is outside, overlapping or off-center.

result: layout check exits 0 in both orientations

Checking win highlights

The tool plays each win and scatter highlight one cell at a time. It renders the frame with and without the highlight and compares the pixels, so it measures what actually lands on screen, layering included. It caught a scatter effect covering its own symbol and sent me the screenshot to decide on.

result: per-cell pass/fail table plus a fail screenshot per cell

Bonus feature audio

A saved run buys the bonus feature through the real UI and plays it out. It then checks that sounds played and stopped in the expected order, and that no console errors appeared.

result: audio-order assertion + zero new errors
How I know it works

Guardrails against false passes

Player path onlyClicks are real mouse events. The skill forbids using script injection to fake an outcome.
Fail fastSaved runs stop at the first failing step, and each step's command and output go in the report.
No weakening testsIf a run fails because of the backend or test data, the agent reports it. It may not loosen the check to make it pass.
Leak checks done rightMemory compares round two against round one, since round one is when assets load for the first time.
Stale build detectionThe skill checks which files the page actually loaded, so a stale build can't pass as a fix.
Errors close every runA visual pass that logs a new console error counts as a failure.
Source code and internal services are left out on purpose. The work belongs to my employer, so this page describes what was built and how it was checked, without the implementation.
